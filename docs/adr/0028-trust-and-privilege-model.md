# ADR 0028 — Trust & privilege model: private network, scoped credentials

- Status: Accepted
- Date: 2026-10-21

## Context

nuck-server must perform operations a normal Matrix user cannot (register users,
create rooms on behalf, auto-join the projector, manage AppServices), so it holds
privileged credentials. The question is how far that trust extends and how the blast
radius is bounded.

## Decision

**Least-privilege, scoped credentials (option c).**

**Network boundary:**

- Tuwunel, nuck-server, LiveKit, and Postgres communicate on a **private container
  network** (ADR 0012). Only the reverse proxy is exposed.
- Tuwunel's C-S API is **never internet-facing**; the client only ever reaches
  nuck-server (ADR 0001/0013).

**Credentials:**

- **Admin token** — held by nuck-server, used *only* for the narrow set of operations
  that require it (user registration/lifecycle, room creation on behalf, AppService
  management). Stored as a secret; never logged.
- **AppService tokens** — one per AppService (projector + each bot, ADR 0018/0019), so
  a compromised bot cannot act as the projector.
- **Client requests** — authenticated by the **Matrix access token**; nuck-server
  validates it against Tuwunel and acts **as that user**, impersonating via
  AppService only where explicitly required.
- **Secrets** — generated by the installer into `.env`/a secret store; never
  committed; rotatable.

## Consequences

- nuck-server is trusted, but any single credential leak has a **bounded** blast
  radius.
- The substrate is unreachable from the internet, removing a large attack surface.
- Client authentication depends on Tuwunel's session validity; revocation semantics
  are the substrate's (ADR 0009).
- The projector and bot AppService tokens are security-critical (ADR 0019) and need
  rotation and audit.
- Impersonation via AppService must be used surgically; overuse would collapse the
  privilege model back toward (a).

## Verification update (2026-10-21)

Checked against Tuwunel
([verification](../verification/tuwunel.md#2-admin-api--confirmed-with-caveats)):
Tuwunel serves the **Synapse admin API** under `/_synapse/admin` (69/100 endpoints
supported) — user create/modify (`PUT /v2/users/{id}`), deactivate, suspend, reset
password, bulk redact, registration-token CRUD, room state/messages with admin bypass,
federation destination control.

**Refinement:** user impersonation is available directly as
`POST /_synapse/admin/v1/users/{user_id}/login` (mint a token to act as a user) —
**prefer this over AppService masquerading** for the narrow operations that need it,
which tightens the privilege model. Caveat: that endpoint and several user endpoints
are **not served when MAS is active**; we do not use MAS, but this forecloses adopting
it later without a rethink. There is **no backup HTTP endpoint** (see ADR 0034).
